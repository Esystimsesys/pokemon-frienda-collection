# コミットメッセージのルール

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ja/v1.0.0/) を採用する。
要約と本文の書き方は Git 自身の指針（[git-commit](https://git-scm.com/docs/git-commit) /
[SubmittingPatches](https://git-scm.com/docs/SubmittingPatches)）に従う。

## 書式

```text
<型>(<範囲>): <要約>

<本文>

<フッター>
```

- `<範囲>`・本文・フッターは省略してよい。要約だけの1行コミットでもよい
- 型と `:` のあとに半角スペースを1つ入れる
- 日本語で書く。型と範囲だけ英字

例:

```text
feat(search): ひらがなで打ってもカタカナの名前に当たるようにする

NFKC でそろえてから ひらがな→カタカナ に寄せる。ポケモンの名前は
全部カタカナなので、寄せる向きはこちらが自然。
半角カタカナ（ﾋﾟｶﾁｭｳ）も NFKC で拾える。
```

## 型

| 型 | 使うとき |
|---|---|
| `feat` | 機能の追加・変更。画面の見た目や動きが変わるもの |
| `fix` | 不具合の修正 |
| `data` | `src/data/*.json` や `assets/types/*.png` の作り直し（`npm run update` の結果など） |
| `docs` | 文書だけの変更。README・`docs/`・コードのコメント |
| `refactor` | 動きを変えない作り直し |
| `perf` | 速さ・軽さの改善 |
| `build` | ビルドと依存関係。`package.json`・Expo の設定 |
| `ci` | GitHub Actions（`.github/workflows/`） |
| `chore` | 上記に入らないもの。`.gitignore` など |

`fix` と `feat` は Conventional Commits の必須。それ以外は仕様が許している追加分で、
`data` だけこのプロジェクト固有（データ生成が作業の大きな割合を占めるため）。

⚠️ Conventional Commits の `style` は**コードの整形**を指す型なので使わない。
画面の見た目を変えたときは `feat` か `fix` にする。まちがえやすいので型から外してある。

## 範囲

省略可。迷ったら付けない。よく使うもの:

| 範囲 | 指すもの |
|---|---|
| `list` / `detail` / `party` / `trainers` / `record` | ずかん一覧 / じょうほう / パーティー / トレーナー / きろく の各画面 |
| `search` / `filter` / `collection` | 検索 / しぼりこみ / 所持データ |
| `sw` / `pwa` | Service Worker / PWA の設定（`public/`） |
| `ocr` / `icons` / `scripts` | 券面の読み取り / タイプのマーク / その他のスクリプト |

## 要約（1行目）

- **50文字以内をめやす**にする（Git の指針。超えても致命的ではないが、`git log --oneline` で切れる）
- **言い切りで書く**。「直す」「そろえる」「追加する」。「直した」「直します」は使わない
  （英語の imperative mood にあたる。命令形＝これを適用すると何が起きるかを書く）
- 末尾に句点（`。`）を付けない
- 何を変えたかを書く。ファイル名の羅列にはしない

## 本文

- 要約との間に**空行**を1行入れる
- 1行は**72文字くらい**で折り返す
- **「なぜ」を書く**。「どうやって」はコードを見れば分かる。具体的には:
  1. 変える前は何が問題なのか（現在形で書く。「〜だった」ではなく「〜になっている」）
  2. 変えたあとがなぜ良いのか
  3. 他に検討して採らなかった案と、その理由
- 料金・仕様など裏付けが要ることは、参照した一次情報のURLを本文に残す

## フッター

- **後方互換を壊す変更**は、型のあとに `!` を付けるか、`BREAKING CHANGE:` を書く。
  このアプリで該当するのは、**所持データ（localStorage）の形が変わって
  今まで登録したぶんが読めなくなる**ような変更。子供の記録が消えるので、
  必ずどちらかで明示する。

  ```text
  feat(collection)!: 所持枚数の保存形式を変える

  BREAKING CHANGE: 旧形式のデータは読めなくなる。移行のしかたは
  src/lib/collection.ts の読み込み側に書いた。
  ```

- **`Co-Authored-By:` は付けない**。Claude が書いたコミットでも付けない
  （このリポジトリは個人のもので、だれが書いたかを履歴に残す必要がないため）

## コミットの分けかた

- **1コミット1目的**。「データの作り直し」と「コードの修正」は分ける
- 生成物は、生成したスクリプトの変更と**同じコミット**に入れる
  （例: `export_type_icons.py` の修正と `assets/types/*.png` は一緒に）
- ビルド成果物（`dist/`）はコミットしない。GitHub Actions がアーティファクトとして渡す

## コミットするタイミング

**コミットと push は、作業を頼んだ人が指示したときだけ行う。**
変更を書き終えたら内容を報告して止まる。Claude に作業させる場合も同じ。

## テンプレート

`.gitmessage` を `commit.template` に設定してある。`git commit`（`-m` なし）で
エディタを開くと、この書式の雛形がコメントとして出る。

クローンし直したときは、1回だけ次を実行する（設定はリポジトリに入らないため）。

```sh
git config commit.template .gitmessage
```
